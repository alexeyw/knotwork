# Pipeline cookbook

A pipeline is a graph of typed nodes. This page is the reference for those
types — what each one does, what decides how it behaves, and where you change
that — followed by recipes that wire them into shapes worth copying.

**One thing to know before you read the node reference.** A node's
configuration sheet in the app shows more than the engine reads. The sheets
were built ahead of some of the behaviour behind them, so a number of fields
accept input, save, and export while nothing consults them during a run — and
the app gives no sign which is which. This page marks every one of them. If a
control you changed made no difference, this is the page that says why.

Where the other pages stop:

- [user-guide.md](user-guide.md) describes the screens: how to open the
  editor, draw a connection, save a pipeline. It is the canonical account of
  how the app behaves.
- [faq.md](faq.md) answers whether a thing exists and where it lives.
- [troubleshooting.md](troubleshooting.md) is for when something is broken.
- [extending.md](extending.md) is for adding a *new* node type in Kotlin.

This page assumes you have the editor open and a pipeline on the canvas. If
you have not got that far, start with
[Pipelines](user-guide.md#pipelines) in the user guide.

## How to read this

Everything from here to [Recipes](#recipes), and the appendix at the end, is
generated from the Kotlin sources that define a node. It is regenerated by
`./gradlew :app:generateCookbookDocs`, a mandatory build check fails when it
drifts, and a unit test holds its claims against the code that runs. What you
read here is what the app does.

Each node's entry answers two questions in order.

**What decides what it does** — the node's real inputs, and where each value
comes from. Usually a field on its configuration sheet; sometimes the graph
around it; occasionally, marked ⚠, nothing you can reach from the app. That
last case is a defect, not a design, and the row says what to do instead.

**Also on the sheet, and ignored by the run** — one line naming the fields
that are stored with the pipeline and exported with it while nothing reads
them. They are listed so you do not spend an evening tuning one. Their
defaults are in the [appendix](#appendix-every-configuration-field).

Three things are worth knowing once rather than fourteen times.

**Ports.** *In* and *Out* are the dots you drag a connection from and to. A
node with two outbound ports is a fork, and which one the run takes is decided
by the node.

**Context.** Each node is given some of the run's context along with its
input, chosen per node under **Input Data** in its sheet. Five blocks exist:
`chatHistory`, `originalTask` (the message that started the run), `nodeInput`
(the previous node's output), `longTermMemory` and `toolResults`. Each type
starts from its own default, because a small on-device model given everything
answers worse than one given the relevant thing.

**Which model runs a node.** Every node that runs on-device uses the model you
have active. Only the LiteRT node's sheet lets you pin a different one; a
pipeline file can pin one for any node, and nothing in the app will show you
that it did.

## Node reference

<!-- AUTO-GEN:NODE_CONFIG -->
### Input — `INPUT`

Where the run starts: your message, a shared page, or the prompt a trigger carries. Exactly one per pipeline.

- **Ports.** No inbound port; one unlabelled outbound port.
- **Context on a new node.** This type ignores the context configuration — it forwards the upstream text unchanged.

**Nothing on this node changes a run.** What it does is fixed; what happens around it is decided by the graph.

### Output — `OUTPUT`

Where the run ends and the answer reaches you. With no prompt of its own it forwards the previous node's text verbatim; give it one and it re-formats that text with one more model pass. Exactly one per pipeline.

- **Ports.** One inbound port; no outbound port.
- **Context on a new node.** `nodeInput` — only when the node has a prompt of its own; in pass-through mode the upstream text is forwarded without any context being composed.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| Whether the answer is re-worded before you see it, and how | the sheet's `systemPrompt` |

### LiteRT — `LITE_RT`

One inference step on the model running on the phone. The default answering node, and the one to reach for unless a step genuinely needs a larger model.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction the model follows | the sheet's `systemPrompt` — a new node arrives with this type's shipped default in it |
| Which model answers | the sheet's `modelId` |

### Cloud — `CLOUD`

One inference step against a configured cloud provider. Everything this node is given leaves the device, so it is a node to place deliberately rather than by default.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `chatHistory`, `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction the model follows | the sheet's `systemPrompt` — a new node arrives with this type's shipped default in it |
| Which provider answers | the sheet's `provider` |

### Intent Router — `INTENT_ROUTER`

Sorts the incoming text into one of the classes you declare and sends the run down the matching branch — the way to give one pipeline several behaviours.

- **Ports.** One inbound port; one outbound port per class declared on the node.
- **Context on a new node.** `chatHistory`, `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction that sorts the message into a class | the sheet's `classifierPrompt` — a new node arrives with this type's shipped default in it |
| Where an answer matching no class goes. Unset, it takes the first branch you connected; set, it takes that class's branch, and terminates when that branch is unwired | the sheet's `fallbackClass` |
| Whether the sorting runs on-device or in the cloud | the sheet's `engineProvider` |
| Which branches exist — one port per class, and the run follows the edge the model picks | the sheet's `classes` |

### If Condition — `IF_CONDITION`

A two-way branch: a yes/no question about the input, or a deterministic check for whether the run carries an image.

- **Ports.** One inbound port; outbound ports **True**, **False**.
- **Context on a new node.** This type ignores the context configuration — it forwards the upstream text unchanged.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| **Checked first:** whether an attached image sends the run down True | the sheet's `branchOnImage` |
| **Checked second:** keywords that send the run down True when the input contains one | the sheet's `keywords` |
| **Checked third:** an input length above which the run goes down True | the sheet's `complexityThreshold` |
| **Checked last:** the yes/no question put to the model | the sheet's `expression` |
| Whether the question runs on-device or in the cloud | the sheet's `engineProvider` |

### Clarification — `CLARIFICATION`

Pauses the run to ask you a question and waits for the answer, which then becomes the node's output. The one node that deliberately stops mid-run.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The question you are asked | the sheet's `questionTemplate` — a new node arrives with this type's shipped default in it |
| The answers offered as chips. Left empty, the model writes them; filled in, yours replace them and stay the same on every run | the sheet's `quickReplies` |
| How long the run waits for your answer | the sheet's `timeoutMs` |

### Tool — `TOOL`

Calls one tool — a built-in, an AppFunction from another app, or one published by an MCP server — and passes the result on. Anything its risk level does not clear waits for your approval.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| Which tool is called — or, left empty, that the model picks one | the sheet's `toolId` |
| Whether every call through this node is confirmed, on top of whatever the tool's risk and your settings already require | the sheet's `alwaysConfirm` |
| Whether the call is composed on-device or in the cloud | the sheet's `engineProvider` |

### Decomposition — `DECOMPOSITION`

Turns one instruction into a list of subtasks. On its own it only produces the list; pair it with a Queue Processor to work through it.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction that produces the subtask list | the sheet's `planningPrompt` — a new node arrives with this type's shipped default in it |
| How many of the produced subtasks are kept | the sheet's `maxSubtasks` — 5 when a file leaves it unset, as the sheet shows |
| Whether the planning runs on-device or in the cloud | the sheet's `engineProvider` |

### Queue Processor — `QUEUE_PROCESSOR`

Walks a list of subtasks one at a time, sending each down the Item branch and taking the Done branch when the list is empty. The only node that can send a run backwards.

- **Ports.** One inbound port; outbound ports **Item**, **Done**.
- **Context on a new node.** This type ignores the context configuration — it forwards the upstream text unchanged.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| What a failing subtask does to the run: end it, or become that subtask's result and let the next one start | the sheet's `stopOnError` |

### Evaluation — `EVALUATION`

Judges what the previous step produced and answers Pass, Retry or Fail — the node that lets a pipeline have another go instead of handing you a bad answer.

- **Ports.** One inbound port; outbound ports **Pass**, **Retry** (conditional), **Fail**.
- **Context on a new node.** `originalTask`, `nodeInput`, `toolResults`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction that judges the result | the sheet's `criteriaPrompt` — a new node arrives with this type's shipped default in it |
| Whether the judgement runs on-device or in the cloud | the sheet's `engineProvider` |
| Whether the node has a Retry branch at all — it does not cap how often that branch is taken | the sheet's `maxRetries` |

### Summary — `SUMMARY`

Condenses what several earlier steps produced into one piece of text, typically just before the Output node at the end of a loop.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `originalTask`, `nodeInput`, `toolResults`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| The instruction that combines the results | the sheet's `customPrompt` — a new node arrives with this type's shipped default in it |

### Pipeline — `PIPELINE`

Runs another saved pipeline as a single step and returns its answer — a function call between pipelines, and the way to reuse a branch instead of copying it.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** This type ignores the context configuration — it forwards the upstream text unchanged.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| Which pipeline is run as this step | the sheet's `targetPipelineId` |

### Skill — `SKILL`

Runs a reusable skill: a fixed instruction plus the list of tools that skill may use. The allowlist is enforced when a tool is called, not merely suggested in the prompt.

- **Ports.** One inbound port; one unlabelled outbound port.
- **Context on a new node.** `originalTask`, `nodeInput`.

**What decides what it does**

| What it decides | Where the value comes from |
|---|---|
| Which skill is run — its instruction and its tool allowlist | the sheet's `skillId` |
| Whether the skill runs on-device or in the cloud | the sheet's `engine` |
| Whether every tool call the skill makes is confirmed, on top of whatever the tool's risk and your settings already require | the sheet's `alwaysConfirm` |

## Recipes

Each recipe below is a pipeline you can import and run. The JSON files live in
[docs/recipes/](recipes/) and are checked on every build: they go through the
same parser the app's import uses, and the graphs they produce through the same
validator the editor's validation bar runs. A recipe that stopped importing
would fail the build rather than fail you.

**To use one:** download the `.json` file, then in the app open the **Pipelines**
tab, tap **Import JSON** in the *From browser editor* footer at the bottom of the
list, and pick it. A bundle (the composition
recipe) is detected automatically and imports every pipeline it contains. Once
imported, a pipeline runs when you bind it to a chat and send a message — see
[Binding a pipeline to a chat](user-guide.md#binding-a-pipeline-to-a-chat).

The prompts are deliberately short. They are written for a small on-device
model, which follows a plain imperative sentence far better than a paragraph of
instructions.

### Routing on intent

[`recipes/intent-routing.json`](recipes/intent-routing.json)

```
Input → Router ─ Answer ─→ Answer ────────────────→ Output
               ├ Search ─→ Look it up → Answer from the result ─→ Output
               └ Ask ────→ Ask one question → Answer
```

One pipeline with three behaviours. The router classifies the message, and
each class has its own branch: answer directly, look the fact up with the
search tool first, or stop and ask the user one question when the message is
too vague to act on.

**What to change.** The classes. Each one needs a name, a description the
classifier can act on, and — this is the part that catches people — an outgoing
edge carrying exactly that name as its label. The class list draws the ports;
the run follows the edges. If you add a class and do not connect its port, the
run reaches the router and stops there.

**Put the class you would rather fall back to first.** When the model's answer
matches no class, the run takes the node's *first* outgoing edge, so the order
of connections is a real decision rather than a drawing detail. Here that is
`Answer`.

**Why the same message can take different branches.** The router sees the chat
history by default, so the same sentence genuinely is a different question in a
fresh chat than after ten turns. If you want the classification repeatable,
turn **Chat history** off under **Input Data** on the router — at the cost of
it no longer understanding follow-ups.

### A list of subtasks, worked through one at a time

[`recipes/decompose-and-queue.json`](recipes/decompose-and-queue.json)

```
Input → Plan → Each subtask ─ Item ─→ Do the subtask ─┐
                    ↑                                  │
                    └──────────────────────────────────┘
               Each subtask ─ Done ─→ Put it together → Output
```

The Decomposition node turns the request into a list; the Queue Processor walks
it. The **Item** branch runs once per subtask, and the edge from the end of
that branch back to the Queue Processor is what makes it a loop — it is the one
edge in the whole format allowed to point backwards. When the list is empty the
**Done** branch fires once.

**What to change.** The body of the loop. Here it is a single on-device model
step; it can be a tool call, a chain, or a whole sub-pipeline. Whatever it is,
its last node must connect back to the Queue Processor, or the run ends after
the first subtask.

**Watch the length.** Every subtask is a step, and a run has a step ceiling — a
plan of twenty subtasks will hit it and stop to ask whether it may carry on.
Keep the planning prompt asking for a short list.

### A tool call you approve

[`recipes/tool-with-approval.json`](recipes/tool-with-approval.json)

```
Input → Draft the note → Save it (write_file) → Confirm
```

The model writes the text, the Tool node writes the file. `write_file` is not a
read-only tool, so by default the run pauses and asks you before it happens —
the approval card appears in the chat and the run resumes on your answer. What
is asked about is governed by the approval settings; the risk level is the
tool's own. This is the whole
point of the shape: the model decides *what*, you decide *whether*.

**What to change.** The tool. Every tool declares a risk level, and that is
what decides whether you are asked; you can also ask to be prompted for a tool
that would not otherwise stop. See
[Approving a tool call](user-guide.md#approving-a-tool-call).

**The Tool node does not take typed arguments from the sheet.** It is given the
node's input and the model produces the call from it, so the node before a Tool
node should produce exactly the text the tool needs — nothing else. That is why
the drafting node here is told to reply with the note text only.

### A run that uses long-term memory

[`recipes/memory-aware-run.json`](recipes/memory-aware-run.json)

```
Input → Answer with memory → Output
```

Three nodes, and the whole recipe is one checkbox and one line of JSON. The
model node has **Long-term memory** enabled under Input Data, so relevant
remembered entries are retrieved and given to it along with the question.

**The line of JSON is `memoryRetrievalQuery`,** declared at pipeline level. It
matters for pipelines that run in the background — from a trigger, a schedule
or the Quick Settings tile. Those runs carry a fixed authored prompt rather
than something you just typed, and a fixed prompt is a poor search key for
memory. The declared query replaces it. Write it as the *topic to recall*, not
as an instruction:

```json
"memoryRetrievalQuery": "commitments, plans and preferences the user mentioned recently, around $DATE"
```

Omit the key for pipelines that only ever run from a chat.

**What to change.** Whether memory is on at all, and where. Turning it on for
every node is the reflex to resist: retrieval happens for each node that asks
for it, and a router or a tool node rarely answers better for having your
history in its prompt.

### One pipeline calling another

[`recipes/composition-bundle.json`](recipes/composition-bundle.json)

```
Parent:  Input → Answer → Tidy up (Pipeline node) → Output
Sub:                      Input → Tidy → Tidied
```

A Pipeline node runs another saved pipeline as one step: its input becomes that
pipeline's message, and that pipeline's answer becomes the node's output. Reach
for it when a sub-flow is used in more than one place, or when a process has
phases you would rather look at separately.

This recipe is a **bundle** — one file carrying the parent and every pipeline
it calls — because a parent whose target is missing imports as a dangling
reference. The app detects the envelope and imports both.

**What to change.** The sub-pipeline. It is an ordinary pipeline: open it,
edit it, and every parent that calls it gets the change. That is the reuse the
node is for.

**The limits are checked before a run starts.** A pipeline cannot call itself,
directly or through a chain, and compositions can only nest so deep — the
target picker greys out any choice that would break either rule and says which
pipeline is the cause.

### What goes wrong most often

- **A node with every context block turned off.** It would receive an empty
  input, so the editor refuses to save until you enable one. The fix is
  usually `nodeInput`.
- **A router class with no edge.** The class draws a port; nothing connects it.
  The run reaches the router and has nowhere to go.
- **A queue with no edge back to it.** The first subtask runs, the loop never
  closes, and the Done branch never fires.
- **A Pipeline node with no target chosen.** A validation error, exactly like a
  dangling connection — the editor will not save it.
- **An Output node given a prompt by accident.** With a prompt it runs one more
  model pass over the answer instead of showing it, which reads as the model
  paraphrasing itself. Leave it empty unless you want a formatter.
- **A Cloud node placed out of habit.** Everything that node is given leaves
  the device. Use it where the task needs it and keep the rest on-device —
  which is also the faster arrangement more often than people expect.

## Appendix: every configuration field

Every field a node's configuration carries, with its default and whether the run
reads it. Most are on the sheet; a few are not, and the last column says which is
which as well as what the engine does with each one.

- **Yes** — the value is saved onto the node and read while the pipeline runs.
- **Shapes the graph** — the value does not reach the engine as a value, but it
  decides which outbound ports the node has, and the run follows the edges
  those ports carry.
- **Not a setting** — the sheet shows it, and the app fills it in from a choice
  you made elsewhere in the same form. Nothing to change here.
- **Not a control** — no sheet shows it. The field survives only so a pipeline
  file written by an older version round-trips through the app unchanged. There
  is nothing to set and nothing that reads it.
- **No** — a control you can change that changes nothing: stored with the
  pipeline, exported with it, never read during a run. The bracket says what to
  do instead.

**There are no `No` rows left.** There used to be twenty-five, and they were a
defect list rather than a design: a control you could change that changed
nothing. Each was resolved the only two ways it could be.

Nine were wired up — four prompt fields that the sheet *required* and the run
never read, then the intent-router fallback class, the clarification quick
replies, the per-node confirmation, the sub-task cap and the queue's
stop-on-error switch. Twelve were removed, because the engine has no matching
concept: a typed pipeline input, an output format, a parallel queue, hand-mapped
tool arguments, renamed branch labels. Eight became **Not a control** — they had
already lost their controls and were only ever listed here because the verdict
column had no word for "kept for compatibility".

Two fields went the other way, from invisible to editable. `IF_CONDITION` reads a
keyword list and a length threshold *before* it asks the model anything, and
neither had a control at all — an imported pipeline could decide every branch on
a keyword while the sheet said nothing about it.

**The sheet shows the value that runs.** A pipeline file stores each node twice:
the `config` block the run reads, and a `nodeConfig` copy the editor keeps its
form in. A file written outside the app can make the two disagree, so every
**Yes** field below is shown from `config`. A file cannot put one tool, prompt or
confirmation switch on the sheet while the run uses another. The editor's copy
still supplies what only it holds: router classes, the Retry branch, and the
fields marked **Not a control**.

This page is generated from the code that defines a node, so the count above is
not a promise anyone has to keep by hand: a control that stops reaching the run
grows its own row back.
